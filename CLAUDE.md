# Loot Manager — контекст проєкту

Однофайловий вебзастосунок для офіцера ігрового альянсу: веде склад, приймає заявки на
здобич, рахує чергу пріоритетів і видає готовий текст оголошення для ігрового чату.
Повна специфікація — `../ТЗ_Loot_Manager.md` (єдине джерело правди щодо вимог;
оновлюй її разом із кодом).

## ⚠️ Найперше: у цій теці ЖИВУТЬ ДВА ПРОЄКТИ

| Моє (цей проєкт) | Чуже (паралельна сесія Claude) |
|---|---|
| `loot-manager.html`, `tests/`, `deploy.sh`, `data/seed.json`, `cards/`, `docs/` | `index.html`, `README.md`, `data/loot.json`, `icons/`, `frames/`, `portraits/`, `../extracted/_tools/` |

Чужі файли **не редагувати** — вони в `.gitignore` (виняток `!/data/seed.json` — він мій).
Ніколи не роби `git add -A`: одного разу так затягнуло чужі файли в коміт.
Додавай свої файли адресно (`git add loot-manager.html tests/core.test.js`).

Другий застосунок — «Витягування зображень з гри»: каталог здобичі з іконками, який веде
`data/loot.json`. Мій менеджер читає цей файл (див. «Синхронізація каталогу»), але не пише в нього.

## Архітектура

Один HTML-файл, vanilla JS, без збірки й залежностей. Два скрипт-блоки:

* **`<script id="core">`** — `LMCore`: чисті функції без DOM і LocalStorage. Саме його
  витягують тести (`new Function(...)` з тексту блока). Уся математика розподілу тут.
* **`<script id="app">`** — стан, сховище, рендер вкладок, обробники подій.

Сховище: LocalStorage, **один ключ `lootManagerData`**, повний перезапис при кожній зміні.
`schemaVersion: 3`. Каталог предметів і класи — глобальні; гравці, історія, типи івентів
і чернетка сеансу — окремо на кожен альянс (`perAlliance[allianceId]`).

Мови: **ru (дефолт) + en**, словники `I18N.ru` / `I18N.en` мусять мати однакові ключі;
рядки звіту — окремо, у внутрішній константі `REPORT_I18N` всередині ядра (не експортується).
Українська була до v1.2.0, лишилась в git-історії.

## Алгоритм розподілу (сутність)

```
Черга  = скільки штук гравець отримав за `historyDays` (14) + узяте в цьому івенті
Порядок= менша черга → серед рівних ТОП (`useTop`) → рол
Етапи  = ручні рішення → перша група класів → друга група (лише залишки)
```

**v4.0.0: балів більше немає.** Раніше було десять констант (два бали, клас-бонус,
штраф історії, штраф за виграш, чотири ваги рідкості) — вони описували те саме
«хто давно нічого не брав», але не пояснювались альянсу. Лишилось дві:
`historyDays` і `useTop`. Рідкість більше не важить у черзі: одна річ — одна одиниця.

**Два етапи (v3.0.0).** Клас має `group`: `A` — танки та лекарі, `B` — ДД (`groupForClassName`
за назвою: воин/жрец/танк/лекарь/хил → A). Порядок задає `draftSession.firstGroup`, дефолт за
годинником (`defaultFirstGroup`: <15 год → A). Гравець першої групи, який нічого не взяв, у
другому етапі не бере участі; клас-бонус і штрафи порівнюють претендентів **усередині етапу**.
Присутність не відмічається — кандидатом є кожен активний гравець, відбір робить заявка.

Історія рахується за вікно `historyDays` (14) з вагами рідкості 1/2/4/8; скасовані записи
не враховуються. Один гравець отримує щонайбільше одну штуку кожного предмета
(ручне рішення офіцера це обмеження обходить). Нічия → рол, стабілізований `rollMemo`.
Усі константи — у `settings`, редагуються в UI.

далі `http://localhost:8641/loot-manager.html`. Сервер тимчасовий — живе, поки жива сесія.

## Дані

* **Склад** вноситься текстом зі гри: вкладка 4 → «Импортировать состав из текста».
  Формат: заголовок класу (можливо з емодзі), далі рядки `1. Нік — Ур. 64`.
  Апсерт за ніком. З v3.2.0 список **повністю замінює склад**: кого в ньому немає —
  `isActive = false`, хто повернувся — знову активний; ролі й історія не чіпаються,
  гравці не видаляються. UI питає підтвердження й перелічує тих, хто вибуває.
* **Автозасів**: порожня база наповнюється з `data/seed.json` + `data/loot.json` при
  першому відкритті. Спрацьовує **лише** якщо `LMCore.isPristine(db)` — чужі дані недоторканні.
  На `file://` fetch недоступний, засів тихо пропускається.
* **Синхронізація каталогу**: вкладка 4 → «Синхронизировать с каталогом». Upsert за
  `catalogUid`, ручні предмети з тією ж назвою усиновлюються, нічого не видаляється.
  Рідкість гри 0–5 → механіка 4 рівні (`0-1 common, 2 rare, 3 epic, 4-5 legendary`).
* **Картки**: файл `cards/<catalogUid>_<мова>.jpg` з'являється в пікері автоматично;
  немає файлу — плитка стає компактним чипом.

## Конвенції розробки

1. **TDD для ядра.** Нова логіка в `LMCore` — спершу падаючий тест у `tests/core.test.js`,
   потім реалізація. UI перевіряється в браузері через `javascript_tool`.
2. **Коміти** — Conventional Commits, теги `vX.Y.Z` на кожну помітну зміну.
   Мажорна версія — коли змінюється спосіб роботи користувача, не обсяг коду.
3. **ТЗ оновлюється разом із кодом.** Зміна поведінки без правки `../ТЗ_Loot_Manager.md`
   вважається незавершеною.
4. **Числа в документації** тримає `tests/docs.test.js`. Додав факт у цей файл —
   додай перевірку туди ж.

## Граблі (перевірено болем)

* `<details open>`, вставлений через `innerHTML`, **сам кидає подію `toggle`** — не можна
  слухати її як «користувач розгорнув». Слухай клік по `<summary>`.
* Зсув липких блоків рахується з фактичної висоти шапки (`--sticky-top`), не константою:
  висота залежить від мови й ширини екрана.
* У панелі прев'ю кадри не компонуються: скріншоти часто падають, а `loading="lazy"`
  не спрацьовує. Для вимірювань став `img.loading = 'eager'` або рахуй із `naturalWidth`.
* `getComputedStyle` повертає **живий** об'єкт: зчитуй значення в примітиви одразу,
  інакше після перерендеру отримаєш порожні рядки.
* Пікер був на CSS-колонках (masonry) через плитки різної висоти, але колонки
  заповнюються згори донизу — заданий порядок розповзався між ними. З v3.1.0 це
  `grid` з `align-items: start`, що читається рядками; порядок задає `PICKER_ORDER`
  (ручний список `catalogUid`, бо каталог ставить усім істотам rarity 4 «Уник.»
  і справжніх ігрових ярусів у даних немає). Повноту списку тримає `tests/docs.test.js`.
* `git` попереджає про LF→CRLF на кожному коміті — це нормально, не помилка.

## Чого не робити

* Не додавати залежності, CDN, збірку — файл мусить лишатися самодостатнім і працювати з `file://`.
* Не перетворювати заявки назад на матрицю гравці×предмети: 70 гравців × 15 предметів = 1050
  чекбоксів, це вже проходили (v2.0.0 замінив її на вибір за предметами).
* Не чіпати `role` як фактор розподілу — це свідомо довідкове поле.
